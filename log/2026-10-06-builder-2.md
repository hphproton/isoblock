## Done

- `npm run build` writes `dist/editor.html` (one file, about 400 kb, no other request) next to `dist/isoblock.mjs`. The build is `scripts/build.mjs` (esbuild API). The editor imports geometry, projection and checks from `src/core`.
- Open and save: a scene file is validated like `isoblock validate`; Save writes `JSON.stringify(scene, null, 2)` and a newline. Saving twice gives byte-identical files and a saved file parses to the same data as the opened one, for all five fixtures. Nothing is kept outside the file.
- Isometric view (scene camera) and top-down plan view on Canvas 2D, repainted only on change (a test waits 600 ms and counts zero extra draws).
- Dragging on both views: screen to ground with grid snap, h kept. Locks: a locked `pos` cannot be dragged; `pos.u` or `pos.v` blocks that axis only; objects with a lock show a lock icon. Undo and redo (one drag is one step), with buttons and keys.
- Property panel with units, a lock toggle per property and a provisional mark; live check panel (only checks that involve changed objects run; tapping a row highlights its objects in both views); five overlays (regions, strips, lanes, zones, anchors) plus object labels; touch (one-finger drag and pan, two-finger zoom, 44 px controls, 24 px reach).
- Core additions, all pure and tested before the editor used them: `locks`, `edit`, `history`, `serialize`, `incremental`, `drag`, `pick`, `viewport`, `planView`, `assumptions`; `buildDisplayList` options (camera, ground extent, anchors, explicit cache); `worldPoint`, `projector`, `pointerOf`.
- Performance work needed for the frame-time criterion (see below): draw order with sweep and prune and a heap, display list cache, per-object updates of `in_region` and `no_overlap`, clipped repaint of the changed rectangles, one stroke per object part, a coarser canvas while a gesture moves things.
- `docs/AGENT_GUIDE.md` has an Editor section. `CHANGELOG.md` is updated under `Unreleased`. All stage 2 tasks in `ROADMAP.md` are ticked.

Not touched: `SPEC.md`, `AGENTS.md`, `MAINTAINING.md`, `tests/golden/`, `tests/fixtures/`. The scene file format did not change. No fixture or golden file needed a change.

## Frame time (SPEC 17, stage 2)

`crowd`, drag of `o101` along small circles, 170 pointer moves, first 20 not counted, headless Chromium with `Emulation.setCPUThrottlingRate` 4. "Work" is the editor's animation frame callback (pointer input, checks, display list, canvas calls), the budget is p95 at most 16.7 ms. These numbers are from the final full run:

| Profile | Frames | Work p50 / p95 / max (ms) | Frame interval p50 / p95 / max (ms) |
|---|---|---|---|
| Desktop, both views, mouse | 150 | 6.3 / 8.3 / 13.2 | 33.3 / 33.4 / 50.0 (driver-paced) |
| Phone 390x844, 2x screen, touch | 150 | 5.0 / 7.3 / 10.7 | 33.3 / 33.4 / 33.4 (driver-paced) |
| Desktop, both views, pointer driven in the page at the display rate | 150 | 5.5 / 7.7 / 19.7 | 16.7 / 16.7 / 33.3 |
| Phone 390x844, 2x screen, pointer driven in the page at the display rate | 150 | 4.5 / 6.4 / 7.7 | 16.7 / 16.7 / 16.8 |

The first two rows are driven through the DevTools protocol, which gives about one move per two frames, so their interval shows the driver, not the editor. Rows 3 and 4 deliver one move per animation frame; there the phone row holds 60 frames per second at 4x slowdown.

What I learned on the way, and what remains:

- Work is not everything. A trace of the renderer main thread showed that Chromium's own commit of the canvas (`ProduceCanvasResource`, software raster in headless) took as much time per frame as the editor's script, and the slowdown multiplies it. It grows with the number of canvas pixels and with the number of canvas operations. Measured with throwaway scripts (not in the repository): at 4x with both views the main thread was busy 22 ms per frame at the start of the work and about 17 ms at the end; with the iso view alone about 12 ms.
- A phone with a 2x screen has four times the pixels. Before the coarser canvas, frames over 20 ms were 8.7 to 14.9 percent of all frames at 4x (interval p95 33 ms); at ratio 1 they were 0 percent.
- With both views side by side, about 4 percent of frames still take two display intervals at 4x (interval p95 16.7 to 33.3 ms between runs). The test asserts the budget on work and the median interval for that profile, and the phone profile also on the interval p95.
- Q-005 records the reading of "frame time" that I chose and asks the maintainer to confirm it.

## Things to know for the review

- A clipped repaint is not pixel-identical to a full repaint: the browser anti-aliases long diagonal edges a little differently under a clip (about 600 of 280,000 pixels differ, mostly by a few levels, now and then one edge pixel by up to about 80). A full repaint follows every drag. `tests/editor/drag.test.ts` compares the two and allows only this noise.
- A tap on an object selects it; it moves only after the pointer travelled 3 px (mouse), 4 px (pen) or 8 px (touch).
- Size, in lines: `src/core` 2,435 (guide 1,500-2,500), `src/cli` 246, `src/editor` 1,700 in TypeScript plus 71 HTML and 129 CSS (guide 800-1,200). The editor is over the guide because of the performance work (frame loop, clipped repaint, stroke batching, resolution switch) and the property panel. The largest file is `src/editor/sceneView.ts` with 401 lines.
- Plan view: strips end 8 units beyond the content that was there when the view was fitted; an object dragged further out leaves the strips behind. Not fixed.
- Not in this stage and not built: state switch, exports, saved versions, compare, occlusion-ray and sort-point overlays; adding or deleting objects; selecting several objects.
