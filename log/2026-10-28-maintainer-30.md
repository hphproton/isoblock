## Scope

Stage 14 is the one ROADMAP planned after stage 13: the editor shows why a layout passes or fails, and the checks say when a value is close to failing. It adds no command and no flag, changes neither the scene format beyond one check parameter nor the runtime file, and needs no new dependency.

## Decisions

- **Warning margins** (SPEC 9.7). A check with one bound takes `warn`, a margin in the unit of its value on the passing side of the bound: a result that would pass is `warn` when its value lies in the margin. That covers `clearance`, `lane_apart`, `visible`, `reachable` (with `max`), `capacity`, `min_screen_size` and `visible_share`. Checks that count objects, and `lane_reaches`, have no distance to a bound, so `warn` there is a schema error. `warn` was already a status of the result shape and of the exit codes; until now no check returned it. `visible_share` in its margin lists the objects inside it, as it lists the failing ones. `describe` gets one `WARN` template per check, because the `FAIL` templates state a comparison (`gap 0.20 < 0.50`) that a warning contradicts; `compare` marks the cell with ` !`.
- **Parts and regions in `hide` and `show`** (SPEC 12). `hide <state> <id>/<part>` and `hide <state> region:<id>` and their `show` forms, which SPEC 17 listed as asked for. An object id still names the object, so the stage 11 commands keep their meaning; object ids may contain `/`, so a part is found by the first split whose left side is an object, as anchors are. `show` of a part drops the object's list when it empties, since an empty list hides nothing; `hideParts` and `hideRegions` stay, as `hide` does since stage 11.
- **Editor.** Checkboxes for parts per state in the property panel and a `Regions` section, as those commands. A `Relations` section that lists `relations --json` live (relations measure footprints and search no grid, so they follow a drag). `Solve` shows the solver's proposal as ghosts with `Apply` (the patch of `solve --patch -`, one history step) and `Discard`, marks the conflict set, and can solve only the selected object. Overlays of relations, sort points, occlusion rays, masks and occluders; the last two wait for the drop like `visible_share`.
- **A test contract for the overlays.** `window.isoblock.overlay(name)` returns the data each overlay draws, and SPEC 10 now defines it. Every overlay is the picture of a command-line output (`relations`, `solve`, the sprites of the runtime file, the `visible` samples, `visibility`, `occluders`), so the editor cases compare the page with the command line of the same build, whose outputs the earlier fixtures check. Only the rays have no command; their samples must give the check's value and occluders.
- **After stage 14** (`ROADMAP.md`): stage 15, lanes and levels, as planned in session 28. SPEC 17 no longer lists paths between levels as unscheduled and names stage 15 for them.
